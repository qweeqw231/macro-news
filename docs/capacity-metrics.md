# 容量口径与实测（2026-11-22）

本文只回答三件事：各体积指标怎么定义、现在是多少、按什么速度涨。阈值沿用
`2026-11-15/data-growth-limits/outputs/capacity-limit-runbook.md`（下称 runbook）。

## 0. 结论

- **「站点月增 343 MB、约 2.3 个月撞 1 GB」不成立。** 343 是把 11-15→11-22 这 7 天里
  一次性抬升的 81.1 MiB 直接年化（×30/7.09）得到的；同一窗口里有 history 导入 +45.8 MiB、
  search 分片落地 +43.6 MiB，这两个是一次性台阶，不是每月都会再发生。
- **稳态**：站点发布 **33 MiB/月**、git 对象 **57 MiB/月**（runbook 实测基线，本次未变）；
  原始写入 churn 约 **1.8~2.4 GiB/天**（工作日高、周末低），没有直接配额。
- **真正最近的一条线是 clone 包**：实测 **143.75 MiB**，黄线 150（约 3 天）、红线 250（约 1.8 个月）。
  这是 clone 体验/预案阈值，不是 GitHub 硬配额。
- 站点 1 GB 按稳态还要 **约 23.6 个月**；仓库 1 GB 约 **14.5 个月**。都不是「几个月内」。
- **2026-11-22 15:32 复核（B1 迁移后）**：`site_mb = HEAD 182.41 + 部署期生成索引 55.57 = 237.98 MiB`；
  clone 包 145.8 MiB；`capacity.mjs` 已改为按此口径统计，并识别一次性台阶（不再输出 2.3 个月）。

## 1. 四个体积的定义与实测

| 指标 | 定义 / 取法 | 实测（2026-11-22 06:3x UTC） |
|---|---|---|
| 本地 `.git` | `.git/` 下全部文件 | **183.44 MiB**（`size-pack` 176.14 + loose 4.73 + 其他） |
| clone 包 | `git rev-list --objects HEAD \| git pack-objects --stdout \| wc -c`，等价一次 clone 的下载量 | **143.75 MiB** |
| 仓库体积（API） | `GET /repos/qweeqw231/macro-news → size`，服务端口径，含元数据 | **186.9 MiB** |
| 站点发布（展开） | 发布产物展开体积：**HEAD 全部 blob + 部署期生成的检索索引**（2.33.1 起 search.json / search-history 不再进 git） | 06:3x 时 **235.06 MiB**（1378 文件）；15:32 时 **237.98 MiB**（HEAD 182.41 + 生成 55.57） |
| Pages artifact | 最近一次 `pages.yml` 的 `github-pages` artifact `size_in_bytes` | **66,448,575 B = 63.37 MiB**（zip，保留 1 天） |

注意：

- `git count-objects` 的 `size-pack` **176.14 MiB** 含不可达对象，比可达 pack 高 22.5%，
  不能当作 clone 下载量；clone 包以 `pack-objects` 的 **143.75 MiB** 为准。
- 站点 1 GB 限制约束的是**展开后的发布内容**（235.06 MiB），不是 63.37 MiB 的 zip artifact；
  artifact 只是部署载体，保留 1 天。
- 本次尝试真实 `git clone` 在 403 秒时被网络中断（`early EOF`），未完成；`pack-objects`
  是 runbook §6.2 定义的等价口径。

## 3. 81 MiB 的来源（为什么 343 不能外推）

11-15 → 11-22 的站点增量按目录拆（runbook 基线 vs 当前）：

| 目录 | 11-15 | 11-22 | 增量 | 性质 |
|---|---|---|---|---|
| `data/history` | 16.84 | 62.66 | **+45.8** | 历史导入，一次性 |
| `data/search.json` + `search-history` 分片 | 11.77 | 55.37（2.21 + 53.16） | **+43.6** | 检索分片落地，一次性 |
| `data/archive` | 36.84 | 43.96 | +7.1 | 稳态，约 1.0 MiB/天 |
| `data/kline` | 61.73 | 65.50 | +3.8 | 含本次 1m 深度约 +0.8 |
| `data/snapshots` | 0.61 | 0.88 | +0.3 | 稳态，约 0.04 MiB/天 |

增量里 **约 89 MiB 是一次性台阶**，正好解释 7 天窗口的 +81~103 MiB（11-15 有两个口径：
runbook 131.7、`capacity.mjs` 快照 153.95）。把它们去年化，就得到 343；剔除后稳态仍是 33。

runbook 在 `data-growth-limits.md` §2 已经踩过同一个坑：30 天口径 115 MB/月里 77 MB 是回补，
当时明确选了稳态 33 作为基线。本次只是把窗口缩到 7 天，台阶占比更高。

## 4. 与 2026-11-15 runbook 的差异

- **阈值与稳态速率没变**：clone 150/250、repo 500/700/1024、site 500/700/1024；57 / 33 MiB/月。
- **基线变了**：clone 72.29 → 143.75、repo 97.3 → 186.9、site 131.7/153.95 → 235.06。
  原因是 history 导入与 search 分片落地，属于 runbook 自己定义的「台阶」。
- 因此 runbook §5 的时间表需要重算：原文「clone 150 → 2027-01」失效，按新基线约 **3 天**；
  「站点 1 GB → 2029-02」按新基线约 **2028-11**，仍同一量级。
- `capacity.mjs` 原先直接拿 7 天速率算 `months_to_hard`，没有剔除台阶（输出 2.3 个月）。
  **2.33.2 已修**：站点/仓库体积一周跳增 >50% 时判为一次性台阶，本期不出月化与 ETA，
  并在备注里写明原因；同时 `site_mb` 改为「HEAD + 部署期生成索引」，与 artifact 展开体积一致。

## 5. 该怎么用这份数字

- 现在该启动的是 runbook 的 **B1（检索数据出 git）**，触发依据是 **clone 150 黄线已到**，
  而不是「站点 1 GB 还剩 2.3 个月」。B1 的对象应包含 `data/search.json` 与
  `data/search-history/`（合计约 55.4 MiB），否则压不下 clone 包。
- 容量周报里的 ETA 现在只在没有一次性台阶时给出；出现台阶会打备注并留空，不要手算年化。
- 站点体积的定义以 `capacity.mjs` 输出为准：`site_mb = site_tracked_mib + site_generated_mib`，
  快照里的 `definitions` 字段逐项写明口径。
- 站点 1 GB、仓库 1 GB 都还有一年以上，不需要现在动。
